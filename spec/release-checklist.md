# TaskPack 출시 점검표

2026-10-01에 하루 동안 1.1.1 · 1.2.0 · 1.2.1 · 1.2.2가 연달아 나갔고, 그 사이 lite 설치 파일이 막히는 결함도 한 번 공개됐다.
원인은 (1) 설치 프로그램을 실제로 돌려 보지 않고 올린 것, (2) 기능을 만들 때 키보드·크기 변화·다중 모니터 같은 기본 점검을 빠뜨린 것,
(3) 요청이 들어올 때마다 바로 출시한 것이다. 이 문서는 그것을 막기 위한 절차다.

## 버전 규칙

- **마이너(1.x.0)**: 새 기능. 요청이 들어와도 바로 올리지 않고 `spec/phases/v1.x.0.md` 계획에 모아서 낸다.
- **패치(1.x.y)**: 이미 공개된 결함 수정만. 새 기능이나 설정 추가를 패치에 섞지 않는다.
- 기능 요청은 다음 마이너 계획에 적고, 사용자가 긴급하다고 하지 않으면 패치로 내지 않는다.

## 출시 순서

1. **계획 확인**: `spec/phases/`의 해당 버전 문서에 범위와 검증 방법이 있다. 미뤄 둔 항목("써 본 뒤 정한다")은 출시 전에 결정했거나 다음 버전으로 명시했다.
2. **자동 시험**: `tests\TaskPack.Tests`에서 `dotnet test` 전부 통과, `dotnet build` 경고 0.
3. **설치 파일 만들기**: `.\build-installer.ps1` (포함판·lite).
4. **설치 시험**: `.\tools\smoke-test-installer.ps1` 이 "모두 통과"여야 한다 (시험용 AppId로 설치·상주 중 덮어 설치·판 바꿔 덮어 설치·제거를 판정한다). 설치 프로그램을 바꾸지 않았어도 매번 돌린다.
5. **직접 써 보기(사전 출시)**: 정식으로 올리기 전에 GitHub **사전 출시(pre-release)** 로 올리고(`gh release create vX.Y.Z --prerelease ...`), 사용자 PC에 설치해 **최소 하루** 쓴다. 문제가 나오면 같은 버전으로 고쳐서 사전 출시를 갱신하고, 정식 번호는 낭비하지 않는다.
6. **정식 승격**: 문제가 없으면 사전 출시 표시를 풀고(`gh release edit vX.Y.Z --prerelease=false --latest`) 홈페이지 다운로드 연결과 링크 미리보기를 확인한다.
7. **기록**: 릴리스 노트에 달라지는 점(특히 상주·자동 실행처럼 사용자가 알아야 하는 것)을 숨기지 않고 쓴다. 결과를 계획 문서에 적는다.

푸시·릴리스는 외부에 공개되는 일이므로 사용자 승인을 받고 한다.

## 기능을 만들 때 설계 점검 질문

계획 단계에서 아래에 답을 적어 둔다. 해당하지 않으면 "해당 없음"과 이유를 적는다.

- **끄면 예전과 같은가?** (새 기능은 기본 꺼짐이 안전한가, 상주·자동 실행처럼 사용자 환경을 바꾸는가)
- **키보드로 되는가?** Tab·방향키·Enter·Esc. 포커스가 다른 앱에서 오는 경우(마우스로만 연 창)는 입력을 가로채지 않는가
- **크기가 바뀌면 위치는?** 알림 띠, 탭 전환, 가방 크기 변경 뒤에도 작업표시줄에 붙어 있는가 (배치 계산은 창 사각형이 아니라 레이아웃이 끝난 크기로)
- **다른 배율·다른 모니터에서?** 이 PC는 작업표시줄 3개(배율 100%·150%)가 있으니 모두에서 확인한다
- **설치·덮어 설치·제거**에서 새 기능이 남기는 것(프로세스, 레지스트리, 파일)을 정리하는가
- **미뤄 두는 설정**이 있다면 지금 정할지, 다음 버전 계획에 적을지
- **시험이 실제 사용자 데이터를 건드리지 않는가** (`TASKPACK_DATA_DIR`, 신호·자동 실행 이름의 시험 꼬리표, 시험용 AppId)

## 일괄 치환 주의

- 여러 파일의 문구를 스크립트로 바꿀 때는 **`git diff`로 바뀐 줄을 눈으로 확인**한다. (1.1.1에서 파이썬 문자열의 `"\10"`이 제어문자로 바뀌어 lite 설치 프로그램이 막힌 사고가 있었다. 경로 문자열은 `chr(92)`나 원시 문자열로 쓴다.)
- 설치 스크립트(`TaskPack.iss`)를 고쳤으면 4번의 설치 시험을 반드시 돌린다.
