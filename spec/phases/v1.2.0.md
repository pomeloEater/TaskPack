# TaskPack 1.2.0 계획 — 클릭 없이 가방 열기

- 상태: **주제 확정, 구현 전** (2026-10-01 김박사 조사). 사용자가 "마우스오버 하나로 집중"(확인이 더 필요한 것 1번)을 확정했다. 2~9번도 사용자가 "권장안대로 진행"으로 확정했다(2026-10-01). 7번(메모리 기준)은 권고가 없었으므로 **상주 대기 중 100MB 이하**를 진행 기준으로 둔다(S1에서 실측 후 조정). 9번(ARM PC)은 기기가 없다고 보고 계속 "확인 못 함"으로 둔다. 진행 순서: 1.1.1(.NET 10 전환) → 1.2.0 S1~S8
- 다음 단계: S1 실험(관문). 통과해야 S3 이후로 간다
- 근거: 이 PC(Windows 11 Pro 빌드 26200, 모니터 3대)의 작업표시줄 실측, Microsoft 공식 문서, SignPath 조건 문서. 확인하지 못한 것은 **미확인(실험 필요)** 으로 적었다

## 목표

**작업표시줄 아이콘에 마우스를 잠깐 올리기만 해도 가방이 열리게 한다.** 클릭으로 여는 지금 방식은 그대로 둔다.

이 기능에는 대가가 있다. 마우스가 어디 있는지 계속 지켜봐야 하므로, 이 기능을 켠 PC에서는 TaskPack이 **늘 뒤에서 켜져 있어야** 한다(이하 "상주"). 지금 TaskPack은 가방을 닫으면 꺼진다. 그래서 1.2.0의 실제 일은 두 가지다.

1. 가방을 닫으면 꺼지는 프로그램을, 켜 두면 계속 기다리는 프로그램으로 바꾼다.
2. 기능을 끈 사람에게는 아무것도 바뀌지 않게 한다. 기본값은 꺼짐(제안)이다.

## 결정 사항 (김박사 제안, 합의 전)

### 1. 상주 구조: 기능을 켠 경우에만 늘 켜 둔다

| | 지금 (1.1.0) | 1.2.0 마우스오버 끔 | 1.2.0 마우스오버 켬 |
|---|---|---|---|
| TaskPack이 켜져 있는 때 | 가방이 열려 있는 동안만 | 지금과 같음 | Windows 시작부터 늘 켜져 있음 (자동 실행을 끄면 그날 첫 클릭부터) |
| 작업표시줄 아이콘 클릭 | 새 TaskPack이 떠서 가방을 연다 | 지금과 같음 | 새 TaskPack은 상주 중인 TaskPack에게 "열어" 신호만 보내고 바로 꺼진다 |
| 가방 닫기 | 프로그램도 꺼진다 | 지금과 같음 | 가방 창만 닫히고 프로그램은 남는다 |
| 알림 영역 아이콘 (시계 옆) | 없음 | 없음 | 있음 (5번 제안) |

- **재클릭 신호의 뜻을 바꾼다.** 지금 `Local\TaskPack.Drawer`는 가방이 열려 있는 동안만 세워 두는 "닫아라" 표지다. 새로 뜬 TaskPack은 이 표지를 보면 신호만 보내고 꺼진다. 상주 TaskPack은 이 표지를 늘 세워 둔다. 뜻을 그대로 두면, 가방이 닫혀 있을 때 아이콘을 눌러도 아무 일이 일어나지 않는다.
  - 그래서 뜻을 "열고 닫기 전환"으로 바꾼다. 신호를 받은 쪽이 지금 가방 상태를 보고 열거나 닫는다.
  - 지금의 400ms 규칙도 그대로 지킨다. 포커스를 잃고 막 숨은 가방은 재클릭으로 보고 다시 열지 않는다.
  - 마우스오버를 끈 상태에서는 결과가 지금과 같다. 신호를 받는 쪽은 언제나 열려 있는 가방이기 때문이다.
- **앞으로 나올 권한을 넘겨준다.** 클릭으로 새로 뜬 TaskPack은 작업표시줄이 띄운 프로그램이라, Windows가 앞으로 나올 권한(포커스)을 준다. 뒤에서 기다리던 상주 TaskPack에게는 이 권한이 없다. 그래서 새 TaskPack이 신호를 보내기 전에 "앞으로 나와도 된다"는 허락(AllowSetForegroundWindow)을 상주 TaskPack에 넘긴다. 이게 안 되면 클릭으로 연 가방이 키보드 입력을 받지 못한다. **미확인(S1 실험)**
- **자동 실행으로 뜬 TaskPack은 가방을 열지 않는다.** 시작용 표시(예: `--background`)를 붙여 실행한다. 이미 상주 중인 TaskPack이 있으면 신호를 보내지 않고 조용히 끝낸다. 로그인하자마자 가방이 뜨는 일을 막기 위해서다.
- 가방 창은 지금처럼 열 때마다 새로 만들고, 닫으면 버린다. 프로그램에는 마우스 감시만 남는다. 지금의 "열 때마다 설정을 새로 읽는" 흐름도 그대로 유지된다.
- 검토한 다른 방식
  - 기능과 상관없이 늘 상주: 모든 기존 사용자에게 메모리 부담과 동작 변화가 생긴다. **기각**
  - 작은 감시 프로그램을 따로 상주시키고, 가방은 지금처럼 새로 띄움: 메모리는 적을 수 있다. 하지만 프로그램이 둘이 되고, 마우스를 올린 뒤 가방이 뜨기까지 지금 클릭할 때만큼 걸린다. **예비안.** S1에서 메모리가 기준을 넘으면 다시 본다

### 2. 마우스오버 감지: 커서 위치는 자주, 아이콘 확인은 멈췄을 때만

- **커서 확인 (폴링, polling: 정해진 간격으로 확인)**: 0.05~0.1초마다 커서 위치만 본다. 커서가 작업표시줄 위가 아니면 거기서 끝나므로 부담이 거의 없다. 대기 중 CPU 사용량은 미확인(S1 측정)이다.
- **후킹(hooking: 마우스가 움직일 때마다 Windows가 TaskPack을 부르게 하는 방식)은 쓰지 않는다.** 공식 문서에 따르면 위험이 둘 있다.
  - TaskPack이 잠깐 바쁘면 Windows 전체의 마우스가 버벅일 수 있다.
  - 정해진 시간(최대 1초)을 넘기면 Windows가 말없이 연결을 끊는다. 프로그램은 끊긴 사실을 알 수 없다.
  - 보안 프로그램이 의심할 가능성도 있다(미확인).
- **아이콘 확인 방법**
  1. 커서가 작업표시줄 위에서 **0.4초** 머문다. Windows 기본 "마우스 머무름" 시간이 400ms다.
  2. 그때 한 번만 UI 자동화(UI Automation: 다른 프로그램의 화면 요소를 읽는 Windows 접근성 기능)로 그 작업표시줄의 TaskPack 버튼을 찾는다.
  3. 커서가 그 버튼 안에 있으면 가방을 연다.
- **이 PC 실측 (2026-10-01)**
  - 작업표시줄 3개(주 모니터 + 보조 2개) 모두에서 TaskPack 버튼이 식별자 `Appid: TaskPack.Drawer`로 보였다. 바로가기와 프로그램에 붙인 식별자(Drawer.AppId)와 같은 값이다.
  - 버튼 이름("TaskPack 고정됨")은 언어와 실행 상태에 따라 바뀌므로 판단에 쓰지 않는다.
  - TaskPack 버튼 하나를 찾는 데 6ms가 걸렸다. 버튼 전체를 읽는 데는 첫 회 75ms, 이후 14~26ms가 걸렸다. Windows PowerShell에서 잰 값이며, TaskPack(.NET 8) 안의 시간은 미확인이다.
  - 두 번 재는 사이에 다른 앱이 열리고 닫혀 TaskPack 버튼이 1116픽셀에서 1083픽셀로 움직였다. 가운데 정렬 작업표시줄은 앱이 열리고 닫힐 때마다 아이콘이 움직인다. 그래서 **위치를 미리 기억해 두지 않고, 머물 때마다 다시 확인한다.**
  - "이 지점에 있는 요소가 무엇인가"를 묻는 방법(ElementFromPoint)은 버튼이 아니라 작업표시줄 전체를 돌려줬다. 쓸 수 없다.
  - 보조 작업표시줄에서 이웃 버튼의 영역이 서로 겹치게 보고된 경우가 있었다. 원인은 미확인이다(S1 확인).
- **한계**
  - 이 식별자는 Windows 11 작업표시줄의 내부 구조이고 공식 약속이 아니다. Windows 업데이트로 바뀔 수 있다.
  - 버튼을 못 찾으면 마우스오버만 조용히 동작하지 않는다. 클릭은 그대로 된다.
  - Windows 10이나 StartAllBack 같은 작업표시줄 교체 프로그램은 구조가 다르다(미확인). 1.2.0의 마우스오버는 **Windows 11 기본 작업표시줄만 지원**할 것을 제안한다.
  - 시작 메뉴 바로가기가 아닌 다른 방법으로 고정했다면 식별자가 다를 수 있다. 이때는 실행 파일 경로로도 맞춰 본다.
- UI 자동화 호출은 가방 화면을 그리는 작업 흐름(스레드)과 다른 뒤쪽 흐름에서 한다. 공식 문서에 따르면 같은 흐름에서 부르면 느려지거나 멈출 수 있다. 탐색기가 바쁘면 답이 늦을 수 있으므로 늦게 온 답은 버린다.

### 3. 마우스오버로 연 가방의 동작

- **포커스를 가져오지 않는다 (제안).** Windows는 사용자가 다른 창을 쓰는 중에 뒤에 있던 프로그램이 앞으로 나오는 것을 막는다(공식 문서). 마우스만 올린 상황에서 TaskPack은 "마지막 입력을 받은 프로그램"이 아니다. 그래서 가방이 키보드 입력을 못 받을 가능성이 높다(S1 확인). 이 제한을 오히려 장점으로 쓴다.
  - 글을 쓰다가 마우스가 아이콘 위를 지나가도, 입력 중인 글자가 가방으로 가지 않는다.
  - 마우스가 가방과 작업표시줄 아이콘 밖으로 나가고 **0.5초**(제안)가 지나면 닫힌다. 고정 핀 버튼을 켜면 닫히지 않는다.
  - 가방 안을 한 번 누르면, 그때부터 클릭으로 연 가방과 같다. 바깥을 누르거나 Esc를 누르면 닫힌다. 칸을 누르면 실행한 뒤 닫힌다(지금과 같음).
- 가방이 이미 열려 있으면 아이콘 위에 머물러도 아무 일이 없다.
- 위치는 지금처럼 마우스가 있는 작업표시줄 쪽, 아이콘 위다.
- 파일을 끌고 가서 작업표시줄 아이콘 위에 머물면 가방이 열려 그대로 넣을 수 있다. 따로 만들지 않아도 생기는 동작이며, 미확인이다.
- 가방이 열려 있는 동안에는 TaskPack 아이콘에 "실행 중인 창"이 생긴다. 그래서 Windows의 툴팁이나 미리보기 창이 가방과 겹칠 수 있다(plan.md의 기존 메모). S1에서 화면을 보고 정한다.

| 사용자가 끄는 곳 | 작업 관리자의 "시작 앱" | 같음 |
| 눈에 보이는가 | 레지스트리라서 보이지 않는다 | 탐색기에서 보인다 |
| 공통 주의 | 작업 관리자에서 "사용 안 함"으로 바꾸면 값이 있어도 실행되지 않는다. Windows가 따로 기록(`StartupApproved`)하기 때문이다. 그러면 설정 스위치와 실제가 어긋날 수 있다 | 같음 |

- Run 값을 권장한다. 표준 방식이고, 켜고 끄는 코드가 가장 단순하다.
- 자동 실행 여부는 config.json에 저장하지 않는다. 레지스트리를 직접 읽어 스위치에 보여 준다. 그래야 백업을 다른 PC에서 불러와도 자동 실행이 몰래 켜지지 않는다. 작업 관리자에서 꺼 둔 경우도 함께 읽어 보여 준다.
- 설치 폴더가 바뀌어 실행 파일 경로가 달라지면, 다음 실행 때 값을 고친다.
- 설치 프로그램에는 자동 실행 체크박스를 넣지 않는다(제안). 켜고 끄는 곳을 설정 화면 하나로 둔다.
- 로그인 직후에는 작업표시줄이 아직 준비되지 않았을 수 있다. 작업표시줄이 없으면 기다렸다가 동작하게 한다. 탐색기가 다시 시작될 때도 같다.

### 5. 알림 영역 아이콘 (시계 옆)

- 제안: 상주 중일 때만 보인다. 메뉴는 "가방 열기 / 설정 / 마우스오버 끄기 / TaskPack 끝내기"다.
- 이유: 늘 켜져 있는 프로그램은 "지금 켜져 있다"는 사실과 "끄는 법"이 보여야 한다. 작업 관리자로만 끌 수 있으면 비개발자에게 어렵다.
- 비용: 프로젝트가 색 고르기 창 때문에 이미 WinForms를 켜 두었다. 그래서 알림 영역 아이콘 기능(NotifyIcon)을 추가 패키지 없이 쓸 수 있다.
- 단점: 작업표시줄 아이콘과 겹쳐 보일 수 있다. Windows 11에서는 "숨겨진 아이콘" 칸 안에 들어갈 수 있다(화면 확인).
- 대안: 알림 영역 아이콘 없이, 설정 창에 "TaskPack 끝내기" 버튼만 둔다.

### 7. 설치·제거 프로그램

- **상주 중에 덮어 설치**: 지금 설정(`CloseApplications=yes`)이 Windows 다시 시작 관리자(Restart Manager)로 실행 중인 TaskPack을 찾아 닫을지 묻는다. 창이 숨어 있는 상주 TaskPack도 제대로 닫히는지는 **미확인**이다(S6 확인).
- 설치가 끝나 TaskPack이 켜지면, 마우스오버를 켜 둔 사용자는 그 순간부터 다시 상주한다. 따로 처리할 필요가 없다.
- **제거**: 제거 프로그램이 자동 실행 값을 지우고, 상주 중인 TaskPack을 끈다. 제거 때도 실행 중인 앱 닫기가 적용되는지는 미확인이다. 적용되지 않으면 제거 프로그램이 종료 신호를 보낸다. SignPath 조건에도 "시스템 변경을 알리고 되돌릴 수 있어야 한다"가 있다.
- "모든 사용자용" 설치를 다른 관리자 계정으로 승인한 경우, 제거 프로그램이 지우는 레지스트리가 사용자의 것이 아닐 수 있다(미확인, 드문 경우).

### 8. 시험 격리 (TASKPACK_DATA_DIR)

- 모든 실행 시험은 `TASKPACK_DATA_DIR`을 `D:\Development2026` 아래 임시 폴더로 지정해서 한다. 실제 `%APPDATA%\TaskPack`은 읽기·백업·삭제·복원 어느 것도 하지 않는다. 시험이 끝나면 그 임시 폴더만 지운다.
- `TASKPACK_DATA_DIR`이 바꾸는 것은 **가방 데이터뿐**이다. 아래는 여전히 실제 것을 쓴다.
  - 작업표시줄 고정 상태와 시작 메뉴 바로가기 (지금도 그렇다)
  - **재클릭 신호 이름**: 상주 TaskPack이 생기면, 시험 중인 TaskPack이 실제 TaskPack에게 신호를 보내 실제 가방을 열 수 있다
  - **자동 실행 레지스트리 값**: 시험판이 실제 값을 개발 폴더 경로로 덮어쓸 수 있다
- 제안: `TASKPACK_DATA_DIR`이 있으면 신호 이름과 자동 실행 값 이름에 시험용 꼬리표를 붙인다. 예: 값 이름 "TaskPack (시험)".
- 마우스오버 감시는 시험판과 실제판이 같은 작업표시줄 아이콘을 본다. 그래서 시험 전에는 실제 TaskPack의 마우스오버를 끈다.
- 이 세션(Claude 앱 안)에서 쓴 레지스트리 값은 실제 사용자 화면과 다르게 보일 수 있다(미확인). 1.1.0 때 `%APPDATA%`에서 비슷한 일이 의심된 적이 있다. 그래서 자동 실행의 최종 확인은 사용자가 직접 로그아웃했다가 로그인해서 한다.

| S6 | 설치·제거 프로그램 | 두 설치 파일을 빌드한다. 이 PC에서는 **덮어 설치만** 한다: 상주 중에 포함판 ↔ lite를 번갈아 설치하면 닫히고 다시 켜지는지 본다. **제거 시험은 Windows 샌드박스**(쓰고 버리는 Windows. 이 PC에서 켜져 있는지는 미확인)에서 한다: 자동 실행 값 삭제, 프로세스 종료를 확인한다. 이 PC에서는 제거의 "가방 데이터도 지울까요"에 답하지 않는다 |

## 확인이 더 필요한 것

1. **[확정 2026-10-01: 예]** 1.2.0을 "작업표시줄 아이콘에 마우스를 올리면 가방 열기" 하나에 집중할까요? 그러려면 **이 기능을 켠 PC에서는 TaskPack이 Windows 시작부터 늘 뒤에서 켜져 있게** 바꿔야 합니다. 기능을 끈 사람에게는 지금과 똑같이 동작합니다. 이 방향에 동의하나요?
   - 제 권장은 **"예"** 입니다.
     - 사용자가 직접 제안한 기능이고, 매일 하는 클릭 한 번을 줄여 줍니다.
     - 기본은 꺼짐이라, 기존 사용자에게 변화가 없고 되돌리기도 쉽습니다.
     - 가장 큰 위험은 S1 실험에서 먼저 확인합니다. Windows 내부 구조 의존, 포커스 규칙, 메모리가 그것입니다. 실패하면 대안 B로 바꿉니다.
2. .NET 8 지원이 11월 10일에 끝납니다. 1.2.0보다 먼저 **1.1.1로 .NET 10 전환만 따로** 낼까요? 권장: 예. 마감이 있는 일이고, 1.2.0 실험 결과와 상관없이 할 수 있으며, 문제가 생겼을 때 원인을 나누기 쉽습니다.
3. 마우스오버 기본값은 꺼짐으로 두고 소개 띠로 알릴까요? 권장: 예. 업데이트만 했는데 프로그램이 상주하기 시작하면 놀랄 수 있습니다.
4. 마우스오버로 연 가방은 포커스를 가져오지 않고, 마우스가 떠나면 닫히게 할까요? 권장: 예. 글을 쓰는 중에 입력을 빼앗지 않습니다. S1에서 포커스를 가져올 수 있다고 나와도 이 방식을 권합니다.
5. 상주 중에는 알림 영역(시계 옆) 아이콘을 둘까요? 권장: 예. 켜져 있다는 사실과 끄는 법이 보여야 합니다.
6. 마우스오버는 Windows 11 기본 작업표시줄만 지원한다고 밝힐까요? 권장: 예. Windows 10과 작업표시줄 교체 프로그램에서는 스위치 옆에 "지원하지 않음"을 표시합니다. README의 "Windows 10 | 11" 배지는 클릭 기능 기준이라 유지합니다.
7. S1 관문의 메모리 기준: 상주 대기 중 작업 관리자 "메모리"가 몇 MB를 넘으면 다시 논의할까요? 권고 없음(사용자 감각의 문제). 참고로 plan.md의 "50~80MB"는 아직 재지 않은 예상값입니다.
8. 코드 서명 준비(자동 빌드로 옮기기, 서명 정책 페이지, SignPath 신청)를 1.2.0과 함께 시작할까요? 권장: 1.2.0이 끝난 뒤 별도로 시작합니다. 자동 실행이 생긴 뒤에 신청해야 "시스템 변경 알림" 조건을 한 번에 맞출 수 있습니다.
9. ARM PC 실기 확인 수단이 있나요(기기, 또는 ARM용 가상 PC)? 없으면 계속 "확인 못 함"으로 둡니다.

S1에서 확인할 미확인 기술 사실
- TaskPack(.NET 8) 안에서 UI 자동화로 버튼을 찾는 시간과 안정성. 보조 작업표시줄에서 버튼 영역이 겹치게 보고된 원인
- 마우스오버로 띄운 가방이 포커스를 가져오지 못하는지
- 권한 넘기기(AllowSetForegroundWindow) 뒤 상주 쪽 가방이 키보드 입력을 받는지
- 상주 메모리와 대기 CPU. 상주 방식과 지금 방식의 열림 시간
- Windows 툴팁·미리보기 창과 가방의 겹침
- 숨은 상주 TaskPack을 설치 프로그램이 닫을 수 있는지(S6), 제거 프로그램에도 앱 닫기가 적용되는지
- 이 PC의 보안 프로그램이 상주·자동 실행·화면 요소 읽기에 반응하는지

## S1 결과 (2026-10-01, 관문 통과)

저장소 밖의 임시 시험 프로그램(.NET 10)으로 이 PC(작업표시줄 3개)에서 쟀다. 가방 데이터는 쓰지 않았다.

| 확인 | 결과 |
|---|---|
| 작업표시줄 3개에서 TaskPack 버튼 찾기 | 모두 `Appid: TaskPack.Drawer`로 찾음. 세 작업표시줄의 버튼 영역이 서로 겹치지 않음(이전 조사의 "겹침"은 재현되지 않음) |
| 커서를 버튼 가운데에 올려 인식 | TaskPack 버튼 **9/9 인식**, 다른 버튼 63곳에서 **오탐 0** |
| 걸리는 시간 (.NET 안) | 버튼 전체 읽기 첫 회 62ms, 이후 16~19ms. 커서 위치 판정 1회 최대 41ms |
| 작업표시줄 밖 | 즉시 "아님"(0ms) |
| 아이콘이 움직이는 중 (앱 열고 닫는 직후 약 2초) | 아이콘이 움직이는 동안은 잠깐 어긋난다(놓침 또는 옛 위치와 달라 보이는 일). 커서가 그 순간 실제로 그 버튼 위에 있었다면 오탐이 아니다. **두 번 읽어 같을 때만 열기**로 방어한다 |
| 상주 대기 (창 없이 0.05초마다 커서만 확인) | 작업 관리자 기준 작업 집합 **39MB**(개인 11MB), CPU는 처음 몇 초를 빼면 약 0.25% |
| 마우스오버로 연 창의 포커스 | **S4로 이월**. 이 시험은 Claude가 띄운 프로그램이라 Windows가 포커스를 줘서 의미가 없었다 |
| 클릭 → 신호로 연 가방이 키보드 입력을 받는지 | **S3로 이월**. 실제 작업표시줄 클릭이 필요하다 |
| 툴팁·미리보기와 가방 겹침 | **S4로 이월**(가방을 실제로 띄운 뒤 화면으로 확인) |
| 탐색기 재시작, 작업표시줄 자동 숨김, 배율 100%·150% 혼용 | 탐색기 재시작·자동 숨김은 사용자 화면을 흔들어 **하지 않았다**. 작업표시줄 3개는 높이가 72·72·48로 배율이 서로 다르며 모두 맞았다 |

판단: **관문 통과.** 메모리는 시험 프로그램 기준 39MB이고, 실제 TaskPack에는 설정 읽기와 아이콘 코드가 더해진다. 100MB 기준에 여유가 있으나 S3에서 실제 TaskPack으로 다시 잰다. 탐색기 재시작·자동 숨김은 S4에서 사용자와 시간을 잡아 확인한다.
